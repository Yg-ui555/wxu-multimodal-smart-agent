# 技术面试要点（无锡学院多模态校园智能助手）

> 这份文档是给面试用的**技术事实清单**，不是宣传稿。
> 每条结论都能在代码里找到出处，能给出数字的都给出数字。
> 面试官追问「这个数是怎么来的」，要能答出**口径**和**测法**——
> 数字本身不重要，**能不能复现**才重要。
>
> 最后更新：2026-10-30。相关文档：[README](../README.md) · [学习指南](LEARNING_GUIDE.md) · [Bad Case 报告](../tests/bad-case-report.md)

## 一、一句话介绍

> 我做了一个面向高校场景的多模态 RAG 助手：把教务处、图书馆、学工处等 7 个子站的通知定时抓下来建成 29631 块的本地向量库，
> 用户用自然语言提问，命中不了关键词也能靠语义找回来；上传校园照片时，用 YOLO-World 零样本识别物体、PaddleOCR 提文字，
> 再接回同一条检索链路；里面接了一个 4 工具的 ReAct Agent，让 LLM 自己决定要不要调检索、课表、OCR、联网。

## 二、系统骨架（背这张图就够）

```
用户问题
   │
   ├─→ 意图判断（intent.py）
   │      ├─ 快捷指令（课表 / 上传 / OCR）──────→ 直接返回
   │      └─ 其他 → ReAct Agent 自主决定调哪个工具
   │                ├─ search_school_notices  → 走下面的检索链路
   │                ├─ get_user_schedule
   │                ├─ ocr_image
   │                └─ web_search（兜底）
   │
   └─→ 检索链路
          BM25（词面精确）  ┐
          向量 bge-m3（语义）┴→ RRF 融合 → top-k → LLM 生成 + 引用
```

**关键点**：检索链路只有一条，多模态和多跳都是「在这条链路前面加东西」，不是另起炉灶。

## 三、高频问题 · 标准答法

### Q1：为什么用 RAG，不微调一个大模型？

**答**：要答的是**数据时效性**而不是「微调更强」。
校园通知（考试时间、奖学金政策、放假安排）每周都在变，微调模型的参数更新成本远高于重建索引；
而且这个项目的知识是**可引用的**——用户要看到「依据哪份文件哪一段」，这要求答案能指回原文，
微调模型做不到「带出处」，RAG 天然可以。

**补一句**：如果目标是「让模型学会某种文体/格式」，那才该微调。本项目要的是「查到最新且能引用的原文」。

### Q2：为什么 BM25 + 向量要一起用？RRF 是什么？

**答**：
- **BM25** 是词面精确匹配（像全文搜索），擅长「教务文号 2024-123」「24电信1」这类专有串，但同义词无能为力。
- **向量检索**（bge-m3 把文本变成一串数字，语义相近的文本数字也相近）擅长同义表达，但精确串容易糊掉。
- 两路各有盲区，所以合并。**RRF（Reciprocal Rank Fusion，倒数排名融合）**只用「名次」不用「分数」：
  `score(d) = Σ 1/(k + rank_i(d))`，k=60。
  为什么用名次不用分数？因为 BM25 的分数和余弦相似度**不在一个量纲**上，没法直接加权相加；
  排名是无量纲的，直接倒数相加就行，这是它最大的优点。
  代价是**丢掉了分数的置信度信息**——排第一但分数很低，和排第一且分数很高，RRF 分不出来。

### Q3：为什么线上把 reranker 关了？

**答**：**做过消融实验（把某个部件拆掉看指标怎么变），结论是关掉更好。**

| 配置 | pass_rate | recall@4 | p50 | p90 |
|---|---|---|---|---|
| 线上同步（BM25 + 向量 RRF，无 reranker） | **61.7%** | 71.7% | 3.01s | 3.69s |
| 评估上限（纯向量 + reranker，关 BM25） | 56.7% | 65.0% | 8.66s | 14.42s |

原因：校园通知里大量精确词（学号、教务文号、奖学金简称）**只有 BM25 抓得准**；
reranker 只能对「已经召回的候选」重排，BM25 命中的精准文档压根没进候选池，重排也救不回来。
所以加了 reranker 反而掉点、延迟还翻 2 倍。

**这题要主动讲**：主动说「我试过加 reranker，实测更差所以没上」比被问到才承认强得多——
这正是「消融实验」这个动作的价值：**每个部件的存在都该有数据支撑，而不是「大家都有我也加一个」。**

### Q4：300 题只有 32.3% 通过率，是不是做得很差？

**答**：不能只看一个数，要看**这个数测的是什么**，而且我保留了旧口径做对照。

三个数字测的是三件不同的事：

| 指标 | 含义 | 60 题 | 300 题 |
|---|---|---|---|
| **recall@4** | 前 4 条检索结果里，有没有召回到含正确答案的文档 | 71.7% | **94.0%** |
| **avg_precision** | 召回的这些文档里，排名靠前的有多少真的相关 | 0.75 | **0.943** |
| **pass_rate** | 最终答案里有没有覆盖住期望关键词 | 61.7% | 32.3% |

**为什么 pass_rate 反而降了**：两套题库的 `expected_keywords` 来源不同——
60 题是 LLM **自己出题时顺手写的**（LLM 答题时容易凑上去，61.7% 偏乐观）；
300 题的关键词是从 **RAG 检索的 top-1 文档里抽的**（关键词确实在文档中，但 LLM 答得简洁口语化，
不一定把每个词都写进答案，32.3% 偏严）。
**同一把尺子从 60 题换到 300 题，刻度就变了**，两个数不能直接比大小。

真正反映「用户能不能搜到有用信息」的是 **recall@4 = 94%**——这才是线上体验。

**诚实版**（README 里也写了）：真正没解决的是 **answer_hit 只有 37%**，
意思是「召回到了，但 LLM 没把关键信息写进答案」。这是 prompt / 答案详略的问题，不是检索的问题。

### Q5：多跳检索怎么实现的？值不值？

**答**：用 LLM 把复杂问题拆成 2~3 个**互相独立**的子问题，每一跳独立走完整混合检索，
最后用 RRF 融合去重。降级策略：拆不出子问题或任何环节异常 → 静默退回单跳。

8 道跨文档题实测：

| 配置 | pass_rate | **recall@4** | 平均延迟 |
|---|---|---|---|
| 基线（单跳） | 50.0% | 75.0% | 1.22s |
| 多跳 | 50.0% | **100.0%** | 1.30s |

**值不值**：延迟只涨 6%（1.22s→1.30s），recall@4 涨 25 个点。多跳那多出来的开销主要是**一次 LLM 拆解**，
而拆解本身也要调 LLM——所以我没开成默认，用 `.env` 的 `USE_MULTIHOP=1` 开关控制，
理由是跨文档问题占比不高，但**开关存在说明可以按场景取舍**。

### Q6：为什么用 ReAct Agent，而不是关键词路由？

**答**：早期版本就是关键词路由（命中「课表」→ 调课表函数），问题很明显：
**同义问法就崩**（「我这周有啥安排」不含「课表」二字），而且每加一个能力就要加一条 if-else。

改成 Agent 之后，**选工具这件事交给 LLM**：
LLM 看到「明天几点上课」和「我期末考啥」这两个问题，自己决定调 `get_user_schedule` 还是 `search_school_notices`。
实现上用 LangChain 的 `AgentExecutor`（tool-calling ReAct），另有一套 LangGraph 实现，
靠 `USE_LANGGRAPH_AGENT` 环境变量切换，两套做对比实验。

**关键工程点**：工具抛异常时**降级成字符串反馈**返回给 Agent，而不是让整个 Agent 崩掉——
Agent 看到「工具报错：xxx」还能自己换个工具重试。

### Q7：本地模型和 API 模型怎么取舍？

**答**：**只有答案生成调 API，嵌入和重排全本地**。

- 嵌入（bge-m3）：每次检索都要把文档转成向量，一天几千次。调 API 的话**钱和延迟都不可控**，而且文档库是固定的，本地跑一次就够。
- 重排（bge-reranker-v2-m3）：同理，而且 reranker 对延迟更敏感（它要过 top-20 候选）。
- 答案生成：这一步需要理解能力、且输出长度不可控，**用大模型 API 才划算**。

顺带一个**性能工程**的细节：本地嵌入走 **Ollama**，并且**常驻进程**不反复起停——
起停的开销远大于推理本身。后来又加了 `EMBED_BASE_URL` 环境变量，让嵌入服务可以指向别的地址（比如换成远程 GPU 机器）。

### Q8：缓存为什么要做三级降级？

**答**：因为**缓存层不能成为新的单点故障**。

```
真 Redis (REDIS_URL) → fakeredis（开发机没装 Redis 时的替身）→ 进程内 LRU（最后的兜底）
```

三级都能用，差别只是性能，**不会因为 Redis 挂了整个问答就不可用**。
TTL 设 7 天，再加 ±10% 的随机抖动——抖动是为了**防缓存雪崩**：
（雪崩 = 大批 key 在同一时刻集中过期，瞬间把数据库/后端打穿；给每个 key 的过期时间加一点随机偏移，
就能把它们错开。）

实测：同一个 query 第二次问，延迟从 21.67s → 2.22s，**加速 10 倍**。

### Q9：定时抓取怎么保证不重复抓、不漏抓？

**答**：靠一个 `crawl_state.json` 状态文件，记录每个监控面（20 个面 / 7 个子站）**上一次抓到的最新条目**。
每次抓取先拿列表页和状态文件比对，只处理比上次新的条目 → 天然幂等，重跑不会重复入库。
清洗后追加进知识库并同步更新向量库和状态文件。

Windows 任务计划每天 02:00 自动跑，`scripts/setup_scheduled_task.ps1` 负责装。

### Q10：多用户怎么隔离？

**答**：浏览器端首次访问生成 UUID 存 cookie，服务端按 UID 分区：
用户历史、会话列表、答案缓存全部带 UID 维度；
课表用 `class_id` 字段**按班级分桶**（24电信1/2/3 各自一桶），
公共课（`class_id IS NULL`）对所有人可见，一句 SQL 就能取到「我的班级 + 公共课」。

### Q11：多模态（拍照识图）是怎么接进来的？

**答**：**不新建链路，只在链路前面加一个「把图片变成文字」的入口**。

1. `image_assistant.py` 判断用户带的是图片还是文字。
2. 带图片 → **YOLO-World** 做零样本检测。
   零样本 = **不给它训练数据，直接用文字标签让它认**。这里用 YOLO-World 而不是普通 YOLO，
   是因为普通 YOLO 只有 COCO 的 80 个固定类，校园里「教学楼」「自行车棚」根本不在里面；
   YOLO-World 支持**开放词汇**，改类别就是改一行 `set_classes(["教学楼", "图书馆", ...])`。
3. 同时走 **PaddleOCR** 提取图片里的文字（截图里的通知正文）。
4. 检测结果 + OCR 文本拼成一条文本查询，接回同一条检索链路。

**权重不进版本库**：`src/yolo/inference.py` 里实现了「本地没有权重就自动从 ultralytics 下载并放回 `weights/`」，
所以 clone 之后第一次跑会自动补齐，仓库不需要背着 32MB 模型。

### Q12：向量库怎么保证不是「残库」？

**答**：构建向量库是**分批**做的（29376 块要跑很久）。断电/中断会留下半成品索引——
一个只有一半文档的索引比没有索引更危险，因为它**看起来能用但答不全**。

所以做了两件事：
1. 构建进度写进单独文件（`_read_progress`），可以断点续跑。
2. **`done=True` 标记只在所有批次都成功时才写**（幂等标记）。没写这个标记就说明这次构建不完整，不能上线。

### Q13：你怎么保证改了代码没弄坏别的地方？

**答**（这题是区分「做过项目」和「做过工程」的地方）：

1. **22 个 pytest 用例**覆盖检索、并发、路由、会话、用户隔离。
2. **300 题评测集**做回归，改 prompt / 改切块 / 改检索模块之后要重跑，指标掉太多就不算改好。
3. **切块参数收敛成单一真相源**（`src/rag/chunk_config.py`）：以前 `chunk_size=800, overlap=150`
   这个值散在 5 个文件里各写一遍，改一处漏三处。现在所有地方都从这里读。

## 四、可能踩的坑（主动交代 = 加分）

| 坑 | 后果 | 怎么处理的 |
|---|---|---|
| pydantic v1/v2 不兼容 | 旧版 pickle 反序列化失败 | 启动时注入兼容补丁，且**失败会显式 warn**，不静默跳过 |
| numpy 2.x 与 imgaug 0.4.0 不兼容 | PaddleOCR 导入失败 | 手动打 5 处补丁（`requirements.txt` 里有写） |
| paddleocr 锁 opencv<=4.6 | 与 numpy 2.x 冲突 | 装完 paddleocr 再用 `--no-deps` 覆盖 opencv 版本 |
| `dict.get(key, default)` 会**先求值 default** | 引用一个不存在的函数 → 每次调用都 NameError | dispatcher 里写错函数名，整条聊天链路 500。**教训：默认参数里的函数名不会被检查到「不存在」** |
| 中文路径 + Windows 编码 | 读 `.gitignore` / 写文件出现乱码 | 统一 UTF-8；脚本读文件显式指定编码 |

## 五、已知短板（**一定要主动说**）

- **多模态端到端没压过测**：YOLO + OCR + RAG 是分模块集成，测试集里只有「图片后纯文字版近似」，
  真实「拍图 → 自动回答」这条链路需要单独 demo 验证。
- **合规过滤是关键词级的**：靠文件名 pattern（"答案"、"A卷"）判断是不是试卷，
  试卷内容被截屏嵌进正常文档里就漏网。合规-拒绝类题目 pass_rate **0%**，这是真问题。
- **BM25 中文切词覆盖不够**：jieba 用通用词表，校园特有词（奖学金类型简称）可能切不准，靠 bge-m3 语义救回一部分。
- **单实例、无高可用**：缓存和监控都做了，但仍是单进程 FastAPI，真高可用要上 Docker Swarm / K8s。
- **YOLO 校园场景泛化有限**：用的是固定类别集，不在类别里的物体识别不到。

> 面试时**主动**说 2~3 条短板 + 「我下一步会怎么做」，比被追问出来强得多。
> 说不完的短板说明没深入过。
